## Context

当前 awesome-selfhosted 仓库包含数千个自托管项目,信息分散在大型 README.md 文件中。用户需要手动浏览、筛选和记录感兴趣的项目,效率低下且缺乏结构化数据支持。现有的 extract_awesome_selfhosted.py 脚本仅做基础提取,缺少完整的元数据采集、中文化和在线浏览功能。

本项目旨在构建一个**独立的静态网站**,将这些项目信息以现代化的方式呈现,支持 Material Design UI、响应式布局、高级搜索和 Vercel 部署。

## Goals / Non-Goals

**Goals:**
- 自动化爬取 awesome-selfhosted 仓库的所有项目信息
- 提取每个项目的开发语言、许可证、功能描述、Star 数等元数据
- 调用 DeepL API 将项目描述和分类翻译为中文
- 抓取 GitHub README 前几段作为项目详细介绍
- 生成基于 Material Design 的响应式静态网站,按分类组织
- 实现前端高级搜索(实时搜索、分类过滤、语言过滤、排序)
- 采用虚拟滚动优化大数据量性能
- 部署到 Vercel,支持在线访问和分享

**Non-Goals:**
- 不实现实时同步机制(仅单次执行)
- 不提供后端服务或数据库存储(纯静态网站)
- 不处理非 GitHub 平台的项目(如 GitLab、Bitbucket)
- 不进行深度代码分析或质量评估
- 不实现用户系统或评论功能

## Decisions

### 决策1: 使用 Python + requests + BeautifulSoup 技术栈
**选择**: 采用 Python 生态的 requests 库进行 HTTP 请求,BeautifulSoup 解析 HTML/Markdown

**理由**: 
- Python 在网络爬虫和文本处理方面有成熟的生态系统
- requests 库简洁易用,支持会话管理、重试机制
- BeautifulSoup 对 HTML 解析能力强,容错性好
- 团队已有 Python 脚本基础(extract_awesome_selfhosted.py)

**备选方案**:
- Node.js + axios + cheerio: 学习成本略高,但性能相当
- Go + colly: 并发性能好,但开发效率较低

### 决策2: 直接从 GitHub API 获取元数据
**选择**: 使用 GitHub REST API v3 获取项目的 language、license、stars 等信息

**理由**:
- API 返回结构化 JSON 数据,无需解析 HTML
- 比网页抓取更稳定可靠
- 支持速率限制内的批量请求(每小时5000次未认证请求)

**备选方案**:
- 解析 GitHub 页面 HTML: 容易受页面结构变化影响,维护成本高
- 克隆仓库读取文件: 网络开销大,速度慢

### 决策3: 采用两阶段处理流程
**选择**: 第一阶段解析 README 获取项目列表,第二阶段逐个查询元数据

**理由**:
- 分离关注点,便于调试和错误处理
- 可以缓存中间结果,支持断点续传
- 第一阶段快速完成,第二阶段可控制速率避免触发 API 限制

**备选方案**:
- 单阶段流水线: 一旦出错难以恢复,不利于进度跟踪

### 决策4: 使用 Jinja2 模板引擎生成 HTML
**选择**: 采用 Jinja2 模板引擎,将 Markdown 格式的模板渲染为 HTML 页面

**理由**:
- Jinja2 是 Python 生态最成熟的模板引擎,功能强大
- 支持模板继承、宏、过滤器,便于组件化开发
- 与 Python 无缝集成,无需额外学习成本
- 性能优秀,支持缓存机制
- 生成的 HTML 可直接部署,无需客户端渲染

**备选方案**:
- 直接生成 Markdown: 简单但缺乏灵活性,难以实现复杂布局
- 使用静态站点生成器(Hugo/VitePress): 功能更强但增加复杂度
- 纯手工拼接 HTML: 维护成本高,易出错

### 决策5: 集成 DeepL Translation API
**选择**: 使用 DeepL API 进行项目描述和分类的中文化

**理由**:
- DeepL 翻译质量业界领先,尤其适合技术文档
- 免费额度充足(50万字符/月),足够处理所有项目
- API 简洁易用,支持批量翻译,节省配额
- 保留原文的同时提供中文,兼顾准确性和可读性

**备选方案**:
- 百度翻译: 国内访问快,但质量略逊,免费额度较少(5万字符/月)
- 有道翻译: 质量中等,需要付费
- 不翻译: 最简单,但降低中文用户可用性

### 决策6: 采用 Material Design + 响应式设计
**选择**: 使用 Material Components Web 实现 UI,采用响应式布局适配移动端和桌面端

**理由**:
- Material Design 是 Google 推出的成熟设计规范,视觉一致性好
- Material Components Web 提供官方实现的组件库,开箱即用
- 响应式设计确保在手机、平板、桌面端都有良好体验
- 符合现代 Web 标准,易于维护和扩展

**备选方案**:
- Bootstrap: 流行但设计风格较为通用
- Tailwind CSS: 灵活但需要自行设计组件
- 自定义 CSS: 完全可控但开发成本高

### 决策7: 实现前端高级搜索(实时搜索 + 防抖)
**选择**: 使用纯 JavaScript 实现前端搜索引擎,支持实时搜索(300ms 防抖)、分类过滤、语言过滤、Star 数范围过滤和多字段排序

**理由**:
- 纯前端实现,无需后端服务,降低架构复杂度
- 实时搜索提供更好的用户体验(输入即搜)
- 防抖机制避免频繁计算,平衡性能和响应速度
- search-index.json 包含所有必要数据,加载一次即可离线搜索
- 对于 ~1500 个项目,前端过滤性能可接受

**备选方案**:
- 按回车搜索: 减少计算次数,但用户体验较差
- 集成 Algolia/Meilisearch: 专业但需要第三方服务,有成本
- 服务端搜索: 需要后端支持,违背静态网站初衷

### 决策8: 采用虚拟滚动优化性能
**选择**: 实现虚拟滚动机制,只渲染可视区域的项目卡片,动态替换内容

**理由**:
- 当项目数量 > 500 时,渲染所有 DOM 节点会导致卡顿
- 虚拟滚动只渲染 ~10-20 个可见项目,性能提升 100x+
- 用户体验流畅,无感知切换
- 纯前端实现,无需额外依赖

**备选方案**:
- 分页: 简单但打断浏览连续性
- 无限滚动: 体验好但仍会积累大量 DOM 节点
- 懒加载图片: 只解决图片加载,不解决 DOM 数量问题

### 决策9: 抓取 GitHub README 前几段
**选择**: 通过 GitHub API 获取项目 README 内容,提取前 3 段(最多 500 字符)作为详细介绍

**理由**:
- 比简短描述提供更丰富的项目信息
- 帮助用户快速了解项目核心功能
- 限制长度避免页面过长,保持浏览效率
- API 获取稳定可靠,比解析 HTML 更优

**备选方案**:
- 仅使用简短描述: 信息量少,不够详细
- 抓取完整 README: 内容过多,影响加载速度
- 不抓取: 最简单,但用户体验较差

### 决策10: 部署到 Vercel
**选择**: 使用 Vercel 平台部署静态网站,配置 vercel.json 实现自动化部署

**理由**:
- Vercel 提供免费静态托管,支持自定义域名
- 自动 HTTPS,全球 CDN 加速
- 零配置部署,与 GitHub 集成良好
- 支持环境变量管理(如 DeepL API Key)

**备选方案**:
- GitHub Pages: 完全免费,但功能较基础,无 CDN 加速
- Netlify: 类似 Vercel,但 Vercel 对前端项目优化更好
- 自建服务器: 成本高,维护复杂

## Risks / Trade-offs

### [风险] GitHub API 速率限制
**影响**: 大量项目可能导致 API 调用超限,脚本被临时封禁

**缓解措施**:
- 实现指数退避重试机制
- 添加请求间隔(如每请求间隔1-2秒)
- 支持可选的 Personal Access Token 提升限额
- 缓存已获取的数据,支持增量更新

### [风险] 项目链接失效或迁移
**影响**: 部分项目可能已删除、改名或迁移到其他平台

**缓解措施**:
- 记录 404/重定向状态,生成问题报告
- 跳过无效链接,不中断整体流程
- 在文档中标记"链接可能失效"的项目

### [风险] Markdown 格式不一致
**影响**: awesome-selfhosted 的 README 格式可能变化,导致解析失败

**缓解措施**:
- 使用正则表达式 + 启发式规则组合解析
- 添加日志记录解析异常的项目
- 定期验证解析结果的完整性

### [风险] DeepL API 配额限制
**影响**: 如果项目数量过多或描述过长,可能超出免费额度(50万字符/月)

**缓解措施**:
- 使用批量翻译 API,减少请求次数
- 限制翻译文本长度(最多 500 字符)
- 缓存翻译结果,避免重复调用
- 监控使用情况,接近限额时发出警告

### [风险] 前端性能问题
**影响**: 大量项目(>1000)可能导致搜索和滚动卡顿

**缓解措施**:
- 实现虚拟滚动,只渲染可见项目
- 搜索使用防抖机制(300ms),避免频繁计算
- 优化 search-index.json 大小,移除不必要字段
- 使用 Web Workers 进行后台计算(如需要)

## Migration Plan

1. **开发阶段**: 
   - 创建 Python 脚本结构(src/ 目录)
   - 实现 README 爬取和解析模块
   - 集成 GitHub API 和 DeepL API
   - 设计 Jinja2 模板(Material Design + 响应式)
   - 实现前端搜索和虚拟滚动

2. **测试阶段**: 
   - 使用小规模样本(单个分类,10-20个项目)验证解析逻辑
   - 测试翻译 API 调用和配额使用
   - 验证前端搜索性能和用户体验
   - 检查响应式布局在不同设备上的表现

3. **执行阶段**: 
   - 运行完整脚本处理所有项目(~1500个)
   - 预计耗时: 2-4小时(取决于 API 速率和网络状况)
   - 生成 output/ 目录的完整网站文件

4. **验证阶段**: 
   - 人工抽查生成的网站质量
   - 测试搜索、过滤、排序功能
   - 验证移动端和桌面端显示效果
   - 修正明显的解析错误或格式问题

5. **部署阶段**: 
   - 配置 vercel.json
   - 部署到 Vercel
   - (可选)绑定自定义域名
   - 验证在线访问正常

**回滚策略**: 保留原始脚本、中间数据和生成的网站文件,如有问题可重新执行或手动修正
